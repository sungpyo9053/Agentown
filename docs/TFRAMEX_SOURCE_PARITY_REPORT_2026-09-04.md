## Upstream behavior that must not be mistaken for product correctness

1. `ParallelPattern` really calls registered agents concurrently, but it gathers child exceptions into artifacts and returns a normal `FlowContext`. TFrameX parity alone therefore does not justify Agentown `SUCCEEDED`.
2. `Flow.execute()` and several patterns turn exceptions into assistant messages instead of raising them. The Adapter must preserve this source behavior in its trace, while Agentown's post-runtime result gate maps error artifacts/messages to `PARTIAL` or `FAILED`.
3. Agent-Builder's prompt names `SequentialPattern.steps_config`, while TFrameX 1.1.0's constructor requires `steps`. `flow_translator.py` introspects the real constructor and will skip a pattern with missing parameters. Adapter tests must use the real constructor signature, not prompt prose.
4. Agent-Builder topologically appends all Agent/Pattern canvas nodes while a Pattern can also reference those Agent nodes. A parity test must detect duplicate execution rather than assuming the reference UI graph is semantically correct.
5. TFrameX has no Agentown output-schema or natural-language requirement gate. These remain an Agentown post-runtime acceptance layer, not a replacement runtime.

## Required target boundary

```text
Korean NL input
  -> Agentown Compiler (Agent, Prompt, Guide, Schema, immutable Version, Capability state)
  -> Agentown IR
  -> thin TFrameX Adapter (registration + translation only)
  -> pinned TFrameX Flow / Agent / Tool / Pattern runtime
  -> source-parity execution trace
  -> Agentown schema + semantic acceptance gate
  -> SUCCEEDED | PARTIAL | FAILED | EXECUTION_NOT_CONFIGURED
```

Both Agent Development UI simulation and downloaded packages invoke the same pinned Core Runtime artifact. The legacy Automation path remains isolated in `BuilderService.executeFrom()` and is not used for Agent Development execution.
